# 체크카드 소비 자동 캡처 & 분석 에이전트

> 한 줄 요약: 실시간 배너 스크린샷 OCR 기반 캡처 파이프라인으로 개인 소비 데이터를 수집하고, LangGraph 멀티 에이전트가 분류·이상탐지·주간 브리핑을 수행하는 개인 금융 에이전트.

## 1. 프로젝트 개요

- **목표**: 체크카드 결제를 캡처 → 카테고리 분류 → 이상지출 탐지 → 주간 소비 브리핑까지, 최소한의 사용자 개입(결제 순간의 물리적 제스처 1회)만으로 동작하는 파이프라인 구축
- **배경**: 카드사 결제 알림이 SMS를 지원하지 않고, iOS는 서드파티 앱의 push 알림 내용을 다른 앱이 읽을 수 있는 공식 API를 제공하지 않음. 이 제약 위에서 스크린샷 OCR 기반 캡처로 아키텍처를 설계함. 완전 무개입은 iOS 플랫폼 제약상 불가능하며, "사용자가 배너를 보고 반사적으로 반응하는 최소 동작 + 이후 전 과정 자동화"를 현실적 목표로 잡음.

## 2. 요구사항 반영

| 항목 | 내용 |
|---|---|
| 스택 | Python 3.11+, Docker/devcontainer, LiteLLM, Gemini API, Groq API, LangGraph, Chroma |
| 진행 방식 | 개인 repo에서 git flow 진행, 주 단위 컴포넌트 추가 |

## 3. 시스템 아키텍처

### 3.1 데이터 캡처 레이어 (실시간 배너 캡처)

```
결제 알림 배너 인지 (사용자)
→ 뒤로 탭 2회 → 시스템 스크린샷 캡처 (조건: 화면 켜짐 상태)
→ 뒤로 탭 3회 → 단축어 실행
  - 최근 사진 가져오기 (Screenshots, 1건)
  - Live Text OCR로 원문 텍스트 추출
  - 캡처 시각(timestamp) 첨부
→ FastAPI 웹훅으로 POST (Authorization 토큰 포함, body: {raw_text, captured_at})
```

파싱/정규화는 클라이언트(단축어)에서 하지 않는다. 단축어의 책임은 캡처 + OCR + 전송까지로 한정하고, 정규식/LLM 기반 구조화는 전부 서버(3.2)에서 처리한다 — 로직 변경 시 단축어 재배포 없이 서버만 수정하면 되고, 디버깅도 서버 로그 한 곳으로 모을 수 있음.

### 3.2 백엔드 (FastAPI)

| 엔드포인트 | 역할 |
|---|---|
| `POST /webhook/capture` | 캡처 요청 수신, 토큰 인증, payload 검증, raw_text 파싱 |

- **정규화 로직**: 원문 텍스트(`raw_text`) → 정규식/LLM 기반 파싱 → `{날짜, 가맹점명, 금액, 원본텍스트해시}` 구조화
- **중복 방지**: 원본텍스트해시 기준. 동일 캡처가 네트워크 재시도 등으로 중복 전송되는 경우를 걸러낸다 (단일 트랙이라 트랙 간 dedup 문제는 발생하지 않음).
- **캡처 시각 검증**: `captured_at`이 서버 수신 시각 대비 지나치게 오래된 경우(예: 네트워크 지연으로 오래된 스크린샷이 뒤늦게 전송됨) 자동 저장하지 않고 리뷰 큐로 이동

### 3.3 저장소

- **관계형 DB** (SQLite로 시작, 필요시 Postgres): 정형 트랜잭션 레코드
- **Chroma**: 가맹점명/거래 설명 임베딩 저장 → 신규 거래의 카테고리 유사도 검색 + 자연어 질의응답용 인덱스 (임베딩 모델: TBD — Gemini 임베딩 API 또는 로컬 모델 중 1주차에 결정)

### 3.4 에이전트 레이어 (LangGraph)

| 노드 | 역할 |
|---|---|
| Categorization | 신규 거래 → Chroma에서 유사 과거 거래 검색 → LLM이 카테고리 확정 (애매하면 리뷰 큐로) |
| Anomaly Detection | 최근 기간 대비 이상치 판단 — 룰 기반 임계치(TBD: 이동평균+표준편차 초과 / 카테고리별 예산 초과 등, 3주차 전까지 확정) + LLM 심각도 분류 병행 |
| Weekly Briefing | RAG로 해당 주 레코드 취합 → 소비 패턴 요약 생성 |
| Natural Language QA (stretch) | 자연어 질의에 응답 (예: "이번 주 배달비 얼마 썼어?") |

**리뷰 큐 통합**: OCR 파싱 실패, 카테고리 애매 케이스를 하나의 리뷰 큐로 통합하고 `reason` 필드로 구분한다 (`ocr_parse_fail` / `category_ambiguous`).

### 3.5 LLM 라우팅 (LiteLLM)

- **Groq**: 카테고리 분류처럼 저지연이 중요한 태스크
- **Gemini**: 주간 브리핑처럼 긴 컨텍스트 요약/설명형 태스크

## 4. 보안 설계

- webhook 인증: `Authorization` 헤더에 랜덤 토큰, 토큰 없는 요청은 거부
- 전 구간 HTTPS
- 원문 텍스트는 파싱 후 폐기, 구조화된 필드만 영속 저장
- payload 형식 검증으로 비정상 요청 필터링
- 토큰, Slack webhook URL 등 민감정보는 `.env`로 관리하고 `.gitignore`에 포함, repo에 노출 금지

## 6. 리스크 & 대응

| 리스크 | 대응 |
|---|---|
| 카드사 SMS 알림 미지원 | 스크린샷 OCR 트랙으로 아키텍처 전환 |
| Back Tap 오작동/미인식 | 2회(캡처)-3회(전송) 두 단계 제스처 분리 + 화면 켜짐 상태 조건으로 오발송 방지 |
| 네트워크 실패/캡처 누락으로 거래 영구 유실 | 배치 백필 트랙이 없어 자동 보정 수단이 없음. 단축어에서 웹훅 응답 실패 시 사용자에게 알림 표시하는 정도가 최소 안전장치이며, 완전한 복구는 되지 않음 — 배치 트랙 제외에 따른 명시적 트레이드오프 |
| OCR 인식 오류 | 정규식 검증 실패 시 자동 저장 대신 리뷰 큐로 이동 |
| 오래된 스크린샷이 뒤늦게 전송됨 | `captured_at` 검증으로 자동 저장하지 않고 리뷰 큐로 이동 |
