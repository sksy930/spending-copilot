# 체크카드 소비 자동 캡처 & 분석 에이전트

> 한 줄 요약: 실시간 배너 스크린샷 OCR 기반 캡처 파이프라인으로 개인 소비 데이터를 수집하고, 트리거별로 분리된 LangGraph 워크플로우가 분류·이상탐지·주간 브리핑을 수행하는 개인 금융 도구. 유일한 에이전트 루프는 가맹점 판단이 불확실할 때 LLM이 스스로 웹 검색 여부를 결정·반복하는 지점 하나뿐이다.

## 1. 프로젝트 개요

- **목표**: 체크카드 결제를 캡처 → 카테고리 분류 → 이상지출 탐지 → 주간 소비 브리핑까지, 최소한의 사용자 개입만으로 동작하는 파이프라인 구축
- **배경**: 카드사 결제 알림이 SMS를 지원하지 않고, iOS는 서드파티 앱의 push 알림 내용을 다른 앱이 읽을 수 있는 공식 API를 제공하지 않음. 이 제약 위에서 스크린샷 OCR 기반 캡처로 아키텍처를 설계함. "사용자가 배너를 보고 반사적으로 반응하는 최소 동작 + 이후 전 과정 자동화"를 현실적 목표로 잡음.

## 2. 요구사항 반영

| 항목 | 내용 |
|---|---|
| 스택 | Python 3.11+, Docker/devcontainer, LiteLLM, Gemini API, Groq API, LangGraph, Chroma |
| 진행 방식 | 개인 repo에서 git flow 진행, 주 단위 컴포넌트 추가 |

## 3. 시스템 아키텍처

### 3.1 데이터 캡처 레이어 (실시간 배너 캡처)

```
결제 알림 배너 인지 (사용자)
→ 뒤로 탭 2회 → 시스템 스크린샷 캡처 (조건: 화면 켜짐 상태)
→ 뒤로 탭 3회 → 단축어 실행
  - 최근 사진 가져오기 (Screenshots, 1건)
  - Live Text OCR로 원문 텍스트 추출
  - 캡처 시각(timestamp) 첨부
→ FastAPI 웹훅으로 POST (Authorization 토큰 포함, body: {raw_text, captured_at})
```

파싱/정규화는 클라이언트(단축어)에서 하지 않는다. 단축어의 책임은 캡처 + OCR + 전송까지로 한정하고, 정규식/LLM 기반 구조화는 전부 서버(3.2)에서 처리한다 — 로직 변경 시 단축어 재배포 없이 서버만 수정하면 되고, 디버깅도 서버 로그 한 곳으로 모을 수 있음.

### 3.2 백엔드 (FastAPI)

| 엔드포인트 | 역할 |
|---|---|
| `POST /webhook/capture` | 캡처 요청 수신, 토큰 인증, payload 검증, raw_text 파싱 → 즉시 200 응답, 분류/이상탐지 그래프는 비동기 실행 (3.7 참고) |

- **정규화 로직**: 원문 텍스트(`raw_text`) → 정규식/LLM 기반 파싱 → `{날짜, 가맹점명, 금액, 원본텍스트해시}` 구조화
- **중복 방지**: 원본텍스트해시 기준. 동일 캡처가 네트워크 재시도 등으로 중복 전송되는 경우를 걸러낸다 (단일 트랙이라 트랙 간 dedup 문제는 발생하지 않음).
- **캡처 시각 검증**: `captured_at`이 서버 수신 시각 대비 지나치게 오래된 경우(예: 네트워크 지연으로 오래된 스크린샷이 뒤늦게 전송됨) 자동 저장하지 않고 리뷰 큐로 이동

### 3.3 저장소

- **관계형 DB** (SQLite로 시작, 필요시 Postgres): 정형 트랜잭션 레코드 + `merchant_category_map`(가맹점명 → 카테고리 정확 매칭 캐시, 3.4.1 0차 정확 매칭 참고)
- **Chroma**: 목적이 다른 유사도 검색을 컬렉션 2개로 분리한다.
  - `past_transactions`: 가맹점명/거래 설명 임베딩. Categorization 1차 판단(유사 과거 거래 검색), QA 중 가맹점명이 불명확한 질문의 후보 검색에 사용.
  - `industry_classification`: 정부 표준업종분류 DB 임베딩 (TBD — 통계청 표준산업분류(KSIC) 또는 여신금융협회 가맹점 업종코드표 중 1주차에 소스 확정). 과거 거래 이력이 없어 `past_transactions`에서 유사 거래를 못 찾은 신규 가맹점의 업종을 RAG로 매칭할 때 사용 (Categorization 2차 판단, 3.4.1 참고).

  두 컬렉션 모두 관련성으로 후보를 좁히는 진짜 RAG이다. 집계형 질문(날짜/카테고리 조건이 명확한 경우)은 관계형 DB의 구조화 쿼리로 처리하므로 Chroma를 거치지 않는다 (임베딩 모델: TBD — Gemini 임베딩 API 또는 로컬 모델 중 1주차에 결정)

  **이중 저장 원칙**: Chroma는 유사도 랭킹/후보 검색에만 쓰고, 확정된 값(카테고리, 금액 등)은 항상 관계형 DB(SQLite)에 저장한다. Chroma 인덱스가 깨지거나 재구축되어도 원본 데이터 정합성에 영향이 없도록 하기 위함.

### 3.4 처리 레이어 (LangGraph 워크플로우)

트리거가 다른 흐름을 한 그래프로 합치지 않는다. 신규 거래 처리 / 주간 브리핑 / 자연어 QA는 각각 다른 이벤트가 시작점이므로 독립된 그래프 3개로 분리한다. 또한 LangGraph를 쓴다고 전부 "에이전트"는 아니다 — 정해진 순서로 LLM을 호출하는 것은 워크플로우이고, LLM이 스스로 다음 행동(종료할지 더 조사할지)을 결정하는 루프가 있어야 에이전트다. 이 시스템에서 그 조건을 만족하는 곳은 가맹점 판단 루프 하나뿐이다.

#### 3.4.1 신규 거래 처리 그래프 (트리거: webhook 캡처 수신)

| 노드 | 역할 | 성격 |
|---|---|---|
| 0차 정확 매칭 | 정규화된 가맹점명이 SQLite `merchant_category_map`과 완전히 일치하면 즉시 카테고리 확정. LLM/임베딩 호출 없음 | 워크플로우 (AI 미사용) |
| 1차 Categorization (0차 미스 시) | Chroma `past_transactions`에서 유사 과거 거래 검색 → 유사도 충분(≥0.75)하면 즉시 카테고리 확정 | 워크플로우 |
| ↳ 2차 업종분류 DB 매칭 (1차도 미달 시) | Chroma `industry_classification`에서 가맹점명 임베딩으로 정부 표준업종분류 후보 검색(RAG) → 유사도 높은 후보가 있으면 LLM이 후보를 검토해 카테고리 확정 (웹 검색 없이 종료) | 워크플로우 (RAG) |
| ↳ 3차 가맹점 판단 루프 (2차도 애매할 때만 진입) | 1~2차 모두 확신 불가 → LLM이 "지금 정보로 판단 가능한가, 웹 검색이 더 필요한가"를 스스로 결정 → 필요하면 가맹점명으로 웹 검색 → 검색 결과를 반영해 재판단 → 확신이 서면 종료, 재시도 한도(2회) 초과 시 리뷰 큐로 이동 | **에이전트 루프 (유일)** |
| Anomaly Detection | 룰 기반 임계치(TBD: 이동평균+표준편차 초과 / 카테고리별 예산 초과 등, 3주차 전까지 확정) 초과 여부 판단 + LLM은 심각도만 분류 | 워크플로우 |

체크카드 소비는 실제로 소수의 가맹점(스타벅스, 쿠팡, 배민, GS25 등)에서의 반복 결제가 대부분을 차지하고, 동일 가맹점이면 OCR 원문 텍스트도 거의 동일하게 나온다. 0차는 이 점을 이용해 임베딩·LLM 호출 없이 dict lookup만으로 대다수 거래를 끝낸다. 또한 리뷰 큐에서 사람이 확정한 케이스는 `merchant_category_map`에 자동 반영되므로, 운영 기간이 늘어날수록 1~3차(임베딩/LLM 호출)로 넘어가는 비율이 줄어드는 구조다 — "확신 없을 때만 AI를 쓴다"는 설계 원칙을 가장 앞단에서 한 번 더 강화한 것.

가맹점 판단 루프만 에이전트인 이유: LLM이 매 스텝마다 "충분한가 / 더 조사할 것인가"를 판단하고 그 결과로 다음 행동(종료 vs 재검색)을 스스로 고른다. 0차 정확 매칭, 1차 과거 거래 유사도 확정, 2차 업종분류 DB RAG 매칭과 Anomaly Detection은 고정된 순서로 조회·LLM 호출을 많아야 한 번만 거쳐 분류·요약만 하는 워크플로우이며, 다음 행동을 스스로 정하지 않는다.

**툴 정의**

| 도구 | 설명 | 파라미터 |
|---|---|---|
| `search_merchant` | 가맹점명으로 웹 검색해 업종 힌트를 가져온다 | `query: string` |

**LLM 출력 스키마 (매 스텝)**

```json
{
  "decision": "confirm" | "search" | "escalate",
  "category": "string",       // decision=confirm일 때만
  "search_query": "string",   // decision=search일 때만
  "confidence": 0.0,
  "reason": "string"
}
```

**동작 예시 (한 건 트레이스)**

1. 입력: 가맹점명 "쿠팡이츠*엔제리너스", 8,900원 — `merchant_category_map`에 미등록(0차 미스), `past_transactions` 유사도 최고 0.42 (임계치 0.75 미달), `industry_classification` 매칭도 확신 없는 후보만 존재 → 루프 진입
2. LLM 호출 1 → `{"decision": "search", "search_query": "쿠팡이츠 엔제리너스 업종", "reason": "배달앱 결제형이라 실제 업종 불명확"}`
3. `search_merchant("쿠팡이츠 엔제리너스 업종")` 실행 → 스니펫: "엔제리너스 - 커피전문점 프랜차이즈"
4. LLM 호출 2 (검색 결과 반영) → `{"decision": "confirm", "category": "카페", "confidence": 0.88, "reason": "검색 결과로 커피전문점 확인"}`
5. 루프 종료, 카테고리 확정 → DB 저장

`decision: search`가 2회 연속이면 강제로 `escalate` 처리 후 리뷰 큐로 이동한다 (재시도 한도, 6. 리스크 참고).

#### 3.4.2 주간 브리핑 그래프 (트리거: 주 1회 스케줄러)

| 노드 | 역할 |
|---|---|
| Weekly Briefing | 스케줄러가 매주 정해진 시각에 트리거 → SQL로 해당 주 레코드 전체 조회 → LLM이 소비 패턴 요약 생성 → Slack 발송 |

신규 거래 그래프와 트리거·실행 시점이 완전히 분리되어 있다. "해당 주"라는 경계가 이미 확정돼 있어 관련성 기준으로 범위를 좁히는 과정이 없다 — 그냥 고정 기간 SQL 스캔 결과를 LLM 요약기에 넣는 것이므로 RAG가 아니다. 취합 → 요약 → 발송 순서가 고정된 워크플로우이며 에이전트 루프도 없다.

#### 3.4.3 자연어 QA 그래프 (트리거: 사용자 질문, stretch)

| 노드 | 역할 |
|---|---|
| Natural Language QA | 사용자가 질의를 보낼 때 트리거 → 질문 유형에 따라 분기 | - |
| ↳ 집계형 질문 (예: "이번 주 배달비 얼마 썼어?") | 날짜/카테고리 조건으로 text-to-SQL 변환 → DB 집계 조회 → LLM이 답변 문장 생성 | SQL 조회 (RAG 아님) |
| ↳ 가맹점 불명확 질문 (예: "저번에 갔던 그 카페 얼마였지?") | Chroma에서 임베딩 유사도로 후보 거래 검색 → LLM이 답변 생성 | 실제 RAG |

사용자 질문이 트리거라는 점에서 앞의 두 그래프와 구분된다. 대부분의 질문(집계형)은 조건이 명확해 구조화 쿼리로 바로 풀리므로 RAG가 아니다 — 관련성으로 후보를 좁히는 검색이 실제로 필요한 건 가맹점명이 불명확한 소수 케이스뿐이며, 여기서만 Chroma 유사도 검색(RAG)을 쓴다. 두 경로 모두 단발 조회-응답 체인이며 에이전트 루프는 없음 (향후 재질의·후속 조회 루프를 추가하면 에이전트화 가능하나 이번 스코프에서는 제외).

**리뷰 큐 통합**: OCR 파싱 실패, 가맹점 판단 루프가 재시도 한도 내에서 끝내 확신하지 못한 케이스를 하나의 리뷰 큐로 통합하고 `reason` 필드로 구분한다 (`ocr_parse_fail` / `category_ambiguous`).

### 3.5 LLM 라우팅 (LiteLLM)

- **Groq**: 카테고리 분류처럼 저지연이 중요한 태스크
- **Gemini**: 주간 브리핑처럼 긴 컨텍스트 요약/설명형 태스크, 가맹점 판단 루프의 웹 검색 필요 여부 판단 및 검색 결과 반영 판단
- **웹 검색 도구**: 가맹점 판단 루프 전용 (TBD — Gemini grounding 또는 별도 검색 API, 3주차 전까지 결정)

### 3.7 실행 모델: 비동기 처리

LangGraph를 위한 별도 서버(LangGraph Cloud/LangServe 등)는 두지 않는다. 개인 프로젝트, 단일 사용자, 트래픽도 없으므로 FastAPI 프로세스 안에서 그래프를 파이썬 함수로 invoke하는 것으로 충분하다 — FastAPI가 이미 "서버"이고 LangGraph는 그 서버 코드 안의 로직일 뿐이다.

진짜 결정 포인트는 "어디서 실행하냐"가 아니라 "언제 트리거하냐"다. `POST /webhook/capture`가 요청을 받은 뒤 신규 거래 그래프(특히 3차 가맹점 판단 루프 — 웹 검색 왕복으로 수 초가 걸릴 수 있음)를 동기로 다 처리하고 나서 응답하면 안 된다. 단축어(클라이언트) 입장에서는 캡처 저장 성공 여부만 빨리 알면 되고, 분류 결과를 기다릴 이유가 없다.

그래서 웹훅은 캡처를 저장하고 즉시 200 응답하며, 분류/이상탐지 그래프는 FastAPI `BackgroundTasks`(또는 `asyncio.create_task`)로 비동기 실행한 뒤 완료 시 SQLite에 결과를 반영한다. 캡처의 신뢰성(안전장치)과 분류의 지연(에이전트 루프 재시도 등)을 분리하는 것 — 3.1의 "캡처는 최소 동작, 이후 전 과정 자동화" 원칙과 같은 맥락이다.

## 4. 보안 설계

- webhook 인증: `Authorization` 헤더에 랜덤 토큰, 토큰 없는 요청은 거부
- 전 구간 HTTPS
- 원문 텍스트는 파싱 후 폐기, 구조화된 필드만 영속 저장
- payload 형식 검증으로 비정상 요청 필터링

## 6. 리스크 & 대응

| 리스크 | 대응 |
|---|---|
| 카드사 SMS 알림 미지원 | 스크린샷 OCR 트랙으로 아키텍처 전환 |
| Back Tap 오작동/미인식 | 2회(캡처)-3회(전송) 두 단계 제스처 분리 + 화면 켜짐 상태 조건으로 오발송 방지 |
| 네트워크 실패/캡처 누락으로 거래 영구 유실 | 배치 백필 트랙이 없어 자동 보정 수단이 없음. 단축어에서 웹훅 응답 실패 시 사용자에게 알림 표시하는 정도가 최소 안전장치이며, 완전한 복구는 되지 않음 — 배치 트랙 제외에 따른 명시적 트레이드오프 |
| OCR 인식 오류 | 정규식 검증 실패 시 자동 저장 대신 리뷰 큐로 이동 |
| 오래된 스크린샷이 뒤늦게 전송됨 | `captured_at` 검증으로 자동 저장하지 않고 리뷰 큐로 이동 |
| 가맹점 판단 에이전트 루프가 반복 재검색으로 지연/비용 증가 | 재시도 한도(2회) 강제, 초과 시 즉시 리뷰 큐로 이동해 루프 종료 |
| 정부 업종분류 DB의 커버리지/최신성 부족 (신생 가맹점명, 프랜차이즈 하위 브랜드 등 누락) | `industry_classification` 매칭 확신도가 낮으면 즉시 확정하지 않고 가맹점 판단 에이전트 루프(웹 검색)로 폴백 |
