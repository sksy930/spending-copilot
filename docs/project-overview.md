# 체크카드 소비 자동 캡처 & 분석 에이전트

> 한 줄 요약: 실시간 배너 스크린샷 OCR 기반 캡처 파이프라인으로 개인 소비 데이터를 수집하고, 트리거별로 분리된 LangGraph 워크플로우가 분류·주간 브리핑을 수행하는 개인 금융 도구. 에이전트 루프는 딱 두 곳뿐이다 — 가맹점 판단이 불확실할 때 LLM이 스스로 웹 검색 여부를 결정·반복하는 지점(3.4.1), 그리고 자연어 질문에 한 번의 조회로 답이 안 나올 때 LLM이 스스로 추가 쿼리를 결정·반복하는 지점(3.4.3).

## 1. 프로젝트 개요

- **목표**: 체크카드 결제를 캡처 → 카테고리 분류 → 주간 소비 브리핑까지, 최소한의 사용자 개입만으로 동작하는 파이프라인 구축
- **배경**: 카드사 결제 알림이 SMS를 지원하지 않고, iOS는 서드파티 앱의 push 알림 내용을 다른 앱이 읽을 수 있는 공식 API를 제공하지 않음. 이 제약 위에서 스크린샷 OCR 기반 캡처로 아키텍처를 설계함. "사용자가 배너를 보고 반사적으로 반응하는 최소 동작 + 이후 전 과정 자동화"를 현실적 목표로 잡음.

## 2. 요구사항 반영

| 항목 | 내용 |
|---|---|
| 스택 | Python 3.11+, Docker/devcontainer, LiteLLM, Gemini API, Groq API, LangGraph (Chroma/RAG는 MVP 스코프 제외 — 3.3 참고) |
| 진행 방식 | 개인 repo에서 git flow 진행, 주 단위 컴포넌트 추가 |

## 3. 시스템 아키텍처

### 3.1 데이터 캡처 레이어 (실시간 배너 캡처)

```
결제 알림 배너 인지 (사용자)
→ 뒤로 탭 2회 → 시스템 스크린샷 캡처 (조건: 화면 켜짐 상태)
→ 뒤로 탭 3회 → 단축어 실행
  - 최근 사진 가져오기 (Screenshots, 1건)
  - Live Text OCR로 원문 텍스트 추출
  - 캡처 시각(timestamp) 첨부
→ FastAPI 웹훅으로 POST (Authorization 토큰 포함, body: {raw_text, captured_at})
```

파싱/정규화는 클라이언트(단축어)에서 하지 않는다. 단축어의 책임은 캡처 + OCR + 전송까지로 한정하고, 정규식/LLM 기반 구조화는 전부 서버(3.2)에서 처리한다 — 로직 변경 시 단축어 재배포 없이 서버만 수정하면 되고, 디버깅도 서버 로그 한 곳으로 모을 수 있음.

### 3.2 백엔드 (FastAPI)

| 엔드포인트 | 역할 |
|---|---|
| `POST /webhook/capture` | 캡처 요청 수신, 토큰 인증, payload 검증, raw_text 파싱 → 즉시 200 응답, 분류 그래프는 비동기 실행 (3.7 참고) |

- **정규화 로직**: 원문 텍스트(`raw_text`) → 정규식/LLM 기반 파싱 → `{날짜, 가맹점명, 금액, 원본텍스트해시}` 구조화
- **중복 방지**: 원본텍스트해시 기준. 동일 캡처가 네트워크 재시도 등으로 중복 전송되는 경우를 걸러낸다 (단일 트랙이라 트랙 간 dedup 문제는 발생하지 않음).
- **캡처 시각 검증**: `captured_at`이 서버 수신 시각 대비 지나치게 오래된 경우(예: 네트워크 지연으로 오래된 스크린샷이 뒤늦게 전송됨) 자동 저장하지 않고 리뷰 큐로 이동

### 3.3 저장소

- **관계형 DB** (Postgres, docker-compose `db` 서비스): 정형 트랜잭션 레코드 + `merchant_category_map`(가맹점명 → 카테고리 정확 매칭 캐시, 3.4.1 0차 정확 매칭 참고)
- **Chroma (RAG, 현재 스코프 제외)**: 개인 프로젝트라 반복되는 가맹점 종류가 적고 신규 가맹점 발생 빈도도 낮다 — 벡터 검색(과거 거래 유사도 매칭, 정부 표준업종분류 DB 매칭)으로 얻는 이득보다 임베딩 모델 선정·업종분류 DB 소싱·인덱스 유지보수 비용이 더 크다고 판단해 MVP에서는 도입하지 않는다. 0차 정확 매칭에서 걸러지지 않은 거래는 바로 가맹점 판단 에이전트 루프(웹 검색)로 넘긴다 (3.4.1). 나중에 미매칭 거래량이 늘어 LLM/검색 비용이 실제로 문제가 되면(3.4.3 QA의 가맹점 불명확 질문 포함) 그때 재검토한다.

### 3.4 처리 레이어 (LangGraph 워크플로우)

트리거가 다른 흐름을 한 그래프로 합치지 않는다. 신규 거래 처리 / 주간 브리핑 / 자연어 QA는 각각 다른 이벤트가 시작점이므로 독립된 그래프 3개로 분리한다. 또한 LangGraph를 쓴다고 전부 "에이전트"는 아니다 — 정해진 순서로 LLM을 호출하는 것은 워크플로우이고, LLM이 스스로 다음 행동(종료할지 더 조사할지)을 결정하는 루프가 있어야 에이전트다. 이 시스템에서 그 조건을 만족하는 곳은 가맹점 판단 루프(3.4.1)와 자연어 QA의 집계형 질문 루프(3.4.3) 둘뿐이다.

#### 3.4.1 신규 거래 처리 그래프 (트리거: webhook 캡처 수신)

| 노드 | 역할 | 성격 |
|---|---|---|
| 0차 정확 매칭 | 정규화된 가맹점명이 Postgres `merchant_category_map`과 완전히 일치하면 즉시 카테고리 확정. LLM/임베딩 호출 없음 | 워크플로우 (AI 미사용) |
| ↳ 가맹점 판단 루프 (0차 미스 시) | LLM이 "지금 정보로 판단 가능한가, 웹 검색이 더 필요한가"를 스스로 결정 → 필요하면 가맹점명으로 웹 검색 → 검색 결과를 반영해 재판단 → 확신이 서면 종료, 재시도 한도(2회) 초과 시 리뷰 큐로 이동 | **에이전트 루프 (유일)** |

체크카드 소비는 실제로 소수의 가맹점(스타벅스, 쿠팡, 배민, GS25 등)에서의 반복 결제가 대부분을 차지하고, 동일 가맹점이면 OCR 원문 텍스트도 거의 동일하게 나온다. 0차는 이 점을 이용해 임베딩·LLM 호출 없이 dict lookup만으로 대다수 거래를 끝낸다. 또한 리뷰 큐에서 사람이 확정한 케이스는 `merchant_category_map`에 자동 반영되므로, 운영 기간이 늘어날수록 가맹점 판단 루프(LLM 호출)로 넘어가는 비율이 줄어드는 구조다 — "확신 없을 때만 AI를 쓴다"는 설계 원칙을 가장 앞단에서 한 번 더 강화한 것. 과거 거래 유사도 매칭이나 업종분류 DB RAG 같은 중간 단계는 일부러 두지 않았다(3.3 참고) — 개인 프로젝트 규모에서는 미매칭 거래를 바로 에이전트 루프로 넘겨도 LLM 호출 비용이 무시할 만한 수준이기 때문.

가맹점 판단 루프가 에이전트인 이유: LLM이 매 스텝마다 "충분한가 / 더 조사할 것인가"를 판단하고 그 결과로 다음 행동(종료 vs 재검색)을 스스로 고른다. 0차 정확 매칭은 고정된 순서로 조회를 한 번만 거쳐 끝나는 워크플로우이며, 다음 행동을 스스로 정하지 않는다. (자연어 QA 집계형 질문도 같은 이유로 에이전트다 — 3.4.3 참고.)

**툴 정의**

| 도구 | 설명 | 파라미터 |
|---|---|---|
| `search_merchant` | 가맹점명으로 웹 검색해 업종 힌트를 가져온다 | `query: string` |

**LLM 출력 스키마 (매 스텝)**

```json
{
  "reason": "string",         // decision/category보다 먼저 쓴다 — 근거를 정하고 나서 결론을 내리게 하기 위함
  "decision": "confirm" | "search" | "escalate",
  "category": "고정 목록 중 하나, reason과 모순되면 안 됨",  // decision=confirm일 때만
  "search_query": "string",   // decision=search일 때만
  "confidence": 0.0
}
```

`category`는 자유 텍스트가 아니라 고정 목록(`음식점/카페/베이커리/편의점/쇼핑/의류/식료품/교육/여가·오락/의료/미용/교통/기타`)에서만 고른다 — 매번 다른 이름을 만들어내면 `merchant_category_map` 캐시와 주간 브리핑/QA 집계가 카테고리별로 안 모이는 문제가 생기기 때문. `reason`을 `category`보다 먼저 쓰게 한 것도 같은 맥락의 방어책이다: 필드 순서대로 토큰을 생성하는 LLM이 근거 없이 결론부터 정하고 뒤늦게 근거를 끼워맞추는 걸 줄이기 위함 (다만 근거 자체의 사실 정확성까지 보장하진 않는다).

**confidence는 게이트로 쓰지 않는다**: 처음엔 `confidence < 0.7`이면 confirm이어도 강제로 검색시키는 코드 레벨 안전장치를 넣었으나, 실측 데이터(batch_replay 125건)에서 confidence가 정답/오답을 전혀 구분하지 못하는 것으로 확인되어 제거했다 — 명백히 틀린 확정(예: "더벤티"를 커피 체인이 아닌 다른 업종으로, "투썸플레이스"를 베이커리로)도 명백히 맞는 확정(스타벅스, GS25 등)과 똑같이 confidence 0.9~1.0으로 나왔다. 즉 confidence는 근거 없는 추측에도 높게 매겨지는 모델의 자기평가일 뿐이라 임계값을 어디에 두어도 분리력이 없었다. 대신 모델이 스스로 고르는 `decision`(search/escalate) 자체는 실측에서 대체로 신뢰할 만하게 동작했다 — confidence는 로그·감사 용도로만 남겨둔다.

**동작 예시 (한 건 트레이스)**

1. 입력: 가맹점명 "쿠팡이츠*엔제리너스", 8,900원 — `merchant_category_map`에 미등록(0차 미스) → 루프 진입
2. LLM 호출 1 → `{"reason": "배달앱 결제형이라 실제 업종 불명확", "decision": "search", "search_query": "쿠팡이츠 엔제리너스 업종"}`
3. `search_merchant("쿠팡이츠 엔제리너스 업종")` 실행 → 스니펫: "엔제리너스 - 커피전문점 프랜차이즈"
4. LLM 호출 2 (검색 결과 반영) → `{"reason": "검색 결과로 커피전문점 확인", "decision": "confirm", "category": "카페", "confidence": 0.88}`
5. 루프 종료, 카테고리 확정 → DB 저장

`decision: search`가 2회 연속이면 강제로 `escalate` 처리 후 리뷰 큐로 이동한다 (재시도 한도, 6. 리스크 참고).

#### 3.4.2 주간 브리핑 그래프 (트리거: 주 1회 스케줄러)

| 노드 | 역할 |
|---|---|
| Weekly Briefing | 스케줄러가 매주 정해진 시각에 트리거 → SQL로 해당 주 레코드 전체 조회 → LLM이 소비 패턴 요약 생성 → Slack 발송 |

신규 거래 그래프와 트리거·실행 시점이 완전히 분리되어 있다. "해당 주"라는 경계가 이미 확정돼 있어 관련성 기준으로 범위를 좁히는 과정이 없다 — 그냥 고정 기간 SQL 스캔 결과를 LLM 요약기에 넣는 것이므로 RAG가 아니다. 취합 → 요약 → 발송 순서가 고정된 워크플로우이며 에이전트 루프도 없다.

#### 3.4.3 자연어 QA 그래프 (트리거: 사용자 질문, stretch)

| 노드 | 역할 |
|---|---|
| Natural Language QA | 사용자가 질의를 보낼 때 트리거 → 질문 유형에 따라 분기 | - |
| ↳ 집계형 질문 (예: "이번 주 배달비 얼마 썼어?") | 날짜/카테고리 조건으로 text-to-SQL 변환 → DB 집계 조회 → 결과로 충분한지 LLM이 스스로 판단 → 부족하면(예: "지난달보다 늘었어?" 같은 비교 질문) 추가 쿼리를 스스로 요청, 충분하면 답변 문장 생성 후 종료 (재시도 한도 3회, 초과 시 답변 불가로 종료) | SQL 조회 (RAG 아님) — **에이전트 루프** |
| ↳ 가맹점 불명확 질문 (예: "저번에 갔던 그 카페 얼마였지?") | Chroma에서 임베딩 유사도로 후보 거래 검색 → LLM이 답변 생성 | 실제 RAG (미구현 — 3.3 참고) |

사용자 질문이 트리거라는 점에서 앞의 두 그래프와 구분된다. 집계형 질문은 조건이 명확해 구조화 쿼리로 풀리므로 RAG가 아니다 — 관련성으로 후보를 좁히는 검색이 실제로 필요한 건 가맹점명이 불명확한 소수 케이스뿐이며, 여기서만 Chroma 유사도 검색(RAG)을 쓴다(미구현). 집계형 질문 경로는 가맹점 판단 루프와 같은 이유로 에이전트다 — 한 번의 쿼리로 부족한지를 LLM이 스스로 판단하고 다음 행동(종료 vs 추가 쿼리)을 스스로 고른다. 가맹점 불명확 질문 경로는 RAG 자체가 미구현이라 현재는 단발 체인도 못 되는 상태.

**리뷰 큐 통합**: OCR 파싱 실패, 오래된 캡처, LLM/검색 장애로 판단 자체를 못 한 케이스를 하나의 리뷰 큐로 통합하고 `reason` 필드로 구분한다 (`ocr_parse_fail` / `stale_capture` / `llm_unavailable`). 가맹점 판단 루프가 재시도 한도 내에서 끝내 확신하지 못한 케이스(`escalate`)는 카테고리만 비운 채 `transactions` 테이블에 그대로 남는다 — 캡처 자체는 성공했고 판단만 유보된 것이라 리뷰 큐와 구분한다.

### 3.5 LLM 라우팅 (LiteLLM)

- **Groq**: 도구 호출이 필요 없는 저지연 판단/생성 태스크 전부 — 가맹점 판단 루프의 confirm/search/escalate 결정, 자연어 QA 에이전트 루프, 주간 브리핑 요약 (`app/merchant_judgment.py`, `app/query.py`, `app/briefing.py`)
- **Gemini**: 실 웹 검색 하나만 — Google Search grounding(`tools=[{"googleSearch": {}}]`)은 Groq에 없는 기능이라 이때만 Gemini를 쓴다 (`RealSearchTool`)
- **웹 검색 도구**: Gemini Google Search grounding으로 구현 완료 (더 이상 TBD 아님)

Groq 무료 티어가 Gemini보다 한도가 넉넉해서, 실제로 호출 빈도가 높은 판단/QA/브리핑을 Groq로 몰고 빈도 낮은 검색만 Gemini에 남기는 쪽이 운영상으로도 유리하다.

### 3.7 실행 모델: 비동기 처리

LangGraph를 위한 별도 서버(LangGraph Cloud/LangServe 등)는 두지 않는다. 개인 프로젝트, 단일 사용자, 트래픽도 없으므로 FastAPI 프로세스 안에서 그래프를 파이썬 함수로 invoke하는 것으로 충분하다 — FastAPI가 이미 "서버"이고 LangGraph는 그 서버 코드 안의 로직일 뿐이다.

진짜 결정 포인트는 "어디서 실행하냐"가 아니라 "언제 트리거하냐"다. `POST /webhook/capture`가 요청을 받은 뒤 신규 거래 그래프(특히 가맹점 판단 루프 — 웹 검색 왕복으로 수 초가 걸릴 수 있음)를 동기로 다 처리하고 나서 응답하면 안 된다. 단축어(클라이언트) 입장에서는 캡처 저장 성공 여부만 빨리 알면 되고, 분류 결과를 기다릴 이유가 없다.

그래서 웹훅은 캡처를 저장하고 즉시 200 응답하며, 분류 그래프는 FastAPI `BackgroundTasks`(또는 `asyncio.create_task`)로 비동기 실행한 뒤 완료 시 Postgres에 결과를 반영한다. 캡처의 신뢰성(안전장치)과 분류의 지연(에이전트 루프 재시도 등)을 분리하는 것 — 3.1의 "캡처는 최소 동작, 이후 전 과정 자동화" 원칙과 같은 맥락이다.

## 4. 보안 설계

- webhook 인증: `Authorization` 헤더에 랜덤 토큰, 토큰 없는 요청은 거부
- 전 구간 HTTPS
- 원문 텍스트는 파싱 후 폐기, 구조화된 필드만 영속 저장
- payload 형식 검증으로 비정상 요청 필터링
